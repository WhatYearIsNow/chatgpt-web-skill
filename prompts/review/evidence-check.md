## 核验标准（每项证据问三个问题）

1. **真实性**：该证据是原始记录还是转述声明？含不含完整命令输出、退出码、版本号、commit SHA（完整 40 位）？
2. **关联性**：证据与声明的对象（源码树 / commit / run）能否建立**可独立验证**的对应？
   - 源码 ↔ commit：Git bundle（可 clone 后 `git rev-parse HEAD` 核对）或逐文件 SHA-256 清单（**完整 64 位**，短哈希不满足独立核验标准）
   - CI ↔ commit：run 的 headSha 与目标 commit 一致，且给出 run 与各 job 的直接链接
3. **完整性**：声称的覆盖范围（次数、平台矩阵、job 数）与证据内容一一对应，无省略号路径、无缺项。

## 已知格式陷阱（前轮实证，务必规避）

- manifest 用短哈希（16 位）→ 不满足独立核验，必须完整 64 位
- 直链写成 `.../job/xxx` 省略形式 → 必须完整可访问 URL
- URL 解析绕过：本机端点校验含 userinfo/空 query/hash 绕过变体——证据中的配置样本同样按此标准核对
- 交付包内含 CI workflow 定义 ≠ 该 run 实际执行成功——两者分开陈述

## 输出格式（严格遵循）

1. **逐项判定表**：每项证据标注「通过 / 已提供未独立验证 / 不满足」+ 缺什么（如不足）。
2. **关联性结论**：源码↔commit↔CI 三者是否形成可独立验证的闭环；缺环明确指出。
3. **最终裁定**：证据闭环成立 → 批准 {{下阶段}}（此时可确认前轮给出的条件清单中，哪些属部署期验证、不构成当前阻断）/ 仍不批准（仅列证据缺口——**不得引入新的代码审查要求**）。
4. **若批准**：确认部署期验证清单生效（哪些验证留到部署期执行），并给出受控启动方式（如 depth=1 起步、逐级放量条件）。

## 轮次协议提醒

- 本轮裁定为终审性质。若证据仍有缺口，只允许再补一轮证据（同样的核验标准），不允许新增代码审查维度。
